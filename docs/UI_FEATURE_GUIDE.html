Dashboard Padaye — UI Feature Guide

"Dashboard Padaye" is a school management system: a React 19 (Create React App) frontend talking to a Java Spring Boot microservices backend (sibling ../backend repo, routed through a single api-gateway). It covers the full lifecycle of running a school: people & roles, classes/timetables, attendance, academics (homework/notes/exams/question papers/results), fees, communication (notices/messages), and cross-service reporting.

Almost everything is driven by two React contexts — AuthContext (current user, JWT, role-scoped people directories) and DataContext (domain data: classes/exams/homework/notes/results/fees/announcements/holidays). What a user sees is governed by their role, sourced from the first entry of the JWT's roles claim, lower-cased. The left sidebar's navConfig object (in Sidebar.jsx) is the single source of truth for which tabs each role can see.

There are 7 UI-reachable roles: Principal, Headmaster, Teacher, Accountant, Support Staff, Student, Parent — plus a pre-login Guest screen. (The backend also defines an IT_MANAGER bootstrap role with no dashboard in this frontend by design — see Known Limitations.)

Dashboard REAL

tab id: dashboard

Stat cards: Total Students (allStudents.length), Total Staff, Classes, Attendance Today (attendanceApi.getSchoolSummary()), Fees Collected (sum of fees[].paidAmount), Upcoming Exams. Panels: Recent Announcements, Staff Overview table, Upcoming Examinations table, Class Strength progress bars. Greeting text still reads schoolInfo.name from mock data (cosmetic only).

Analytics REAL

tab id: analytics

Pass Rate, Distinction count (90+), Notes Uploaded, Homework Given — computed client-side from useData().results/notes/homework. School Attendance stat card from reportingApi.getAnalytics(). Subject Performance (avg % per subject) and Grade Distribution bar charts, both computed client-side over real results.

APIs: GET /api/reports/analytics via reportingApi.getAnalytics().

User Management (Registration) REAL

tab id: registration → shared Registration.jsx

Lists all users (usersApi.listUsers()), search + role filter, stat cards, View→read-only detail modal. Registers new users of any of 8 roles (only basic account fields — see Known Limitations for the explicit code-comment admission that extended profile fields aren't wired up yet). Only Principal/Headmaster/IT Manager can register; only IT Manager can register a new Principal.

APIs: usersApi.listUsers(), authApi.register() (via registerUser()).

Question Papers REAL

tab id: question-papers → shared QuestionPaperManagement.jsx

canManage=true for principal — can create (2-step wizard: paper-type picker → sections/questions editor, 5 paper types, 7 question types), view, print-preview, and enter/view results for exam-linked papers. Papers cannot be edited once saved (no update endpoint exists).

7th question type: Match the Following (Shuffled) — same two-column pairing as the plain Match the Following type, but Column B is displayed in a randomized, no-fixed-point order (shuffledOrder, a derangement) so it never lines up straight against Column A. Editor has a "🔀 Shuffle Again" control and shows the auto-computed answer key live; the read-only paper viewer gets a .no-print "Show answer key" toggle that highlights the scrambled mapping without affecting the printed sheet.

APIs: academicsApi.listQuestionPapers()/createQuestionPaper(), peopleApi.listStudents(), academicsApi.createResult() (via addResult). shuffledOrder/pairs round-trip through the backend's opaque JSON content blob with zero backend changes required.

Known Limitations / Mock-only / Not Backend-Wired

Every item below is backed by direct code evidence (import statements, missing handlers, or absent API functions), not assumption.

1. Sidebar "unread" badges are hardcoded literals, not real counts

In Sidebar.jsx's navConfig: Principal's Notices badge is the literal string '2', Principal's Messages badge is '3', Teacher's Messages badge is '2', Parent's Messages badge is '1'. None of these are computed from any data source — they are static strings baked into the navigation config object itself.

Evidence: { id: 'messages', icon: '💬', label: 'Messages', badge: '3' } (and similarly for the other three) in Sidebar.jsx.

2. Messages feature (Principal, Teacher, Parent) has zero backend wiring

No messagesApi.js (or any messaging endpoint) exists anywhere in src/api/ — confirmed by listing all 12 files in that directory. Principal's Messages tab is a static placeholder with a dead "+ Compose" button. Teacher's and Parent's MessagesView components both import { users, messages } from '../../data/mockData' and render a read-only thread list from that static array; Teacher's compose form's "Send" button has no onClick at all.

3. Contact Teacher (Parent) never sends anything

ContactTeacher()'s handleSend only toggles a local "sent" toast and clears the form — no fetch/API call of any kind. There is no backend endpoint for teacher-contact messages.

4. Holidays are never persisted to any backend

DataContext.jsx's holidays state is seeded once from mockData.js's initialHolidays export, and addHoliday/deleteHoliday only call setHolidays — no holidaysApi.js module exists, and no holiday endpoints appear in any other API module. Principal/Headmaster's "add/delete holiday" UI (HolidayManagement canEdit) therefore appears to work but is lost on refresh/re-login. Separately, Student's HolidayList and Parent's AcademicCalendar bypass DataContext entirely and import holidays directly from mockData.js, both using a hardcoded cutoff new Date('2026-08-04') to compute "upcoming" — now stale.

5. Dead UI: Teacher's "My Classes" action buttons

MyClasses() in TeacherDashboard.jsx renders "Take Attendance" and "View Students" buttons on every class card with no onClick handler on either.

6. Question papers cannot be edited once saved

academicsApi.js exposes only listQuestionPapers() and createQuestionPaper() — no update or delete function exists. QuestionPaperManagement.jsx's editor only ever POSTs a new paper.

7. No update/delete for exams, homework, notes, or results anywhere in the app

academicsApi.js only has create-functions for each of these (createExam, createHomework, createNote, createResult) alongside their list/get functions — matching the backend's and the project's stated convention of no generic DELETE for low-stakes entities being added "opportunistically" at best, and none having been added yet for these four.

8. Class "delete" is a soft deactivate, not a real delete

classesApi.js has no delete function at all; DataContext.jsx's deleteClass calls classesApi.updateClass(id, { ..., active:false }).

9. Fee records can never be created or deleted via the UI (by design)

feeApi.js exposes only getStatusForStudent, listFeeRecords, payFee, and updateFeeRecord — no create or delete. This is a deliberate financial-record-safety decision documented in docs/PROJECT_CONTEXT.md: "Never add delete for financial records — hide the affordance in the UI instead, matching what the backend intentionally does not expose."

10. Guest sidebar navigation (navConfig.guest) is effectively dead code

App.js's AppContent() renders <GuestHome onLogin={...}/> directly with no <Layout>/<Sidebar> wrapper at all whenever there is no logged-in user — so navConfig.guest's three items (home/notices/calendar) never render in the normal pre-login flow. The only path where Sidebar could render guest nav is if a user is actually authenticated with role === 'guest' (the dashboards.guest branch) — but even then, <GuestHome onLogin={() => {}} /> is rendered without being passed activeTab: GuestHome manages its own fully independent internal tab state ('about'/'holidays', not matching the sidebar's home/notices/calendar ids at all), so clicking those sidebar items would change Layout's internal activeTab state but have zero visible effect. Additionally, the backend's Role enum (per docs/PROJECT_CONTEXT.md) has no GUEST value, yet Registration.jsx still offers "Guest" as one of its 8 registerable roles — a frontend/backend mismatch.

11. Accountant/Support Staff dashboard stat cards use static mock data

StaffPortal.jsx imports schoolInfo from mockData.js and uses schoolInfo.totalStudents/totalStaff/totalClasses directly as stat-card values, never fetched live. There is no schoolApi.js/school-info endpoint anywhere in the app; Principal's dashboard greeting text also still reads schoolInfo.name for display purposes only.

12. Parent portal only ever shows the first linked child

Every view in ParentDashboard.jsx destructures const child = children[0]. If peopleApi.getChildrenForParent returns more than one child, only the first is ever displayed across the dashboard, attendance, results, homework, fees, and contact-teacher screens.

13. Registration explicitly admits incomplete profile fields

Direct code comment in Registration.jsx: "Extended profile fields (subjects, class, roll number, etc.) will be added once the people directory is wired up." Only basic account fields are collected at registration time — there is no way to set a new student's class or a new teacher's subjects from this screen.

14. Two backend-supported API functions have no UI anywhere

timetableApi.createTimetableSlot() — no screen creates/edits timetable slots; every timetable view in the app (Headmaster's school view, Teacher's own, Student's own) is read-only. attendanceApi.getTeacherToday() — also unused by any component.

15. IT Manager has no dashboard

The backend's Role enum includes IT_MANAGER (a narrow bootstrap-only role that creates the first Principal account), and Registration.jsx contains an isItManager branch, but there is no navConfig.it_manager entry and no dedicated dashboard component for this role anywhere in the frontend — by design, per docs/PROJECT_CONTEXT.md.
