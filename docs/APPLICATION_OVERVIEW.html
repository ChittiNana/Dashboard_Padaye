🏫 Dashboard Padaye — Application Overview

A role-based school management portal (branded in-app as "Greenwood School Portal") covering admissions, academics, attendance, exams, fees, and communication for eight distinct user roles — built as a React frontend that can run entirely on its own, with or without the real backend online.

React 19 + React Router 7 Context API state Local mock-data fallback layer 8 roles Spring Boot backend (optional for demo)

📦 What this is

Dashboard Padaye is a full school-management UI: user & role administration, class and timetable setup, attendance tracking, homework/notes distribution, exams & question papers (including a "Match the Following" question type with a shuffled variant), results, fee collection, holidays, notices and internal messaging, plus cross-cutting reports.

It's designed to talk to a real Spring Boot microservices backend (a sibling backend repo, fronted by a single api-gateway), but every screen also works completely stand-alone — see the mock-data layer below — so the UI can be demoed, developed, or tested with no backend running at all.

🧱 Architecture

Frontend

React 19 (Create React App), React Router 7 for routing, two React Contexts as the single source of truth: AuthContext (current user/session, role-scoped people lists) and DataContext (classes, exams, homework, notes, results, fees, notices, holidays).

Backend (optional)

Java Spring Boot microservices behind an API gateway, default base URL http://localhost:8080 (override with REACT_APP_API_BASE_URL). Not required to run or demo the app.

The mock-data fallback layer

Every read first tries the real API; if that call fails (because the backend isn't running, or any network error), it falls back to a local store instead of showing an empty/broken screen. Every write (create / update / delete) is applied to that local store immediately — so the UI feels instantly responsive — and the real API call is still fired in the background on a best-effort basis, ignored if it fails.

  • Store: src/data/mockStore.js — persisted to the browser's localStorage under the key padaye_mock_store_v1.
  • Survives: page reloads and logout/login as a different role (e.g. a Teacher adds a student, logs out, and the Principal immediately sees that student).
  • Auto-resets: after 24 hours (TTL), the store reseeds itself from scratch with fresh demo data so leftover test data doesn't accumulate indefinitely.
  • Helpers: readWithFallback() and writeThroughMock() in src/api/mockFallback.js, used at every data-loading/mutating call site across the app.
This means login itself works offline too — if the real authApi.login call fails, the submitted username/password is checked against a seeded demo users table instead.

👥 Roles & what each one can do

The left sidebar's navigation is entirely role-driven (src/components/Layout/Sidebar.jsx) — a user only ever sees the tabs their role is entitled to.

🗂 Feature highlights

  • Exams & Question Papers — supports 7 question types, including a Match-the-Following type and a shuffled Match-the-Following variant.
  • Attendance — teachers mark daily attendance per class; principal/headmaster see a school-wide summary and per-class breakdown.
  • Fees — fee status and collection tracking, with a per-student pay-fee flow.
  • Timetable — class and teacher timetable views.
  • Communication — notices board and internal messages, scoped per role.
  • Reports — attendance, exam results, fee collection, and staff performance reports for school leadership.
  • Registration — "User Management" screen for creating students, staff, and other accounts.
